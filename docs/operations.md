# Staging validation and production release

**Status: application branch under validation; not deployed.** Production remains unchanged. Read `deployment-access.md` for the one-time key/host setup. Use Node 24 LTS (validated locally on 24.7) or supported Node22 >=22.13; do not use the local machine's old Node23 in production.

**Confirmed hosting split:** Next.js stays on Netlify; MySQL and Socket.IO stay on Hostinger. A separate authenticated media API handles private voice files and FFmpeg on the VPS. This supersedes the earlier assumption that Next.js must run beside voice storage. Follow [VPS-MEDIA-DEPLOYMENT.md](VPS-MEDIA-DEPLOYMENT.md) for this architecture-only change, which adds no migration and does not replace the existing socket service.

## Resource plan for Hostinger KVM 1

These are budgeting ranges, not measurements of the inaccessible VPS. Confirm with the read-only audit and load tests before approving settings.

| Component | Initial memory budget | Deployment decision |
|---|---:|---|
| OS, CloudPanel, Nginx, monitoring | 500–800 MiB | Preserve current config; measure first |
| Existing MySQL | 512–1,024 MiB | Review current buffers/connections; never apply guessed tuning |
| Next.js | Netlify, no VPS process | Keep the existing deployment; public media origin is a build setting |
| One Socket.IO process | 128–384 MiB | No cluster/Redis; retain existing process and measure DB pool |
| One media API plus encoder | 128–256 MiB API estimate plus transient encoding; proposed 512 MiB total service ceiling | Two initial Prisma connections; one bounded FFmpeg job, staged CPU/memory limits |
| coturn | 64–256 MiB plus relay traffic | Optional fallback; measure actual relay usage |
| Group LiveKit | Not reserved on this VPS | Default off. Test separately; no assumption it fits 1 vCPU |

Keep at least 750 MiB available memory under expected peak and >20% free disk; no sustained swap/OOM. Starting voice quota is 1 GiB, max 10,000 notes, at least 1 GiB free-disk reserve. At 64 kbps a two-minute normalized note is approximately 0.96 MB before container overhead; the upload/retention policy bounds costs. Use 90-day sent-note retention and 24-hour unsent drafts; decide production policy with the owner.

Native direct P2P sends negligible media through this VPS unless TURN is selected. Two 720p streams at 1–2.5 Mbps each require about0.9–2.25GB/hour of TURN outbound traffic, plus inbound and protocol overhead. Four-person SFU video at 1.5 Mbps per participant produces approximately18Mbps outbound (8.1GB/hour) and6Mbps inbound before screen share/overhead. These are bitrate arithmetic, not measured codec or provider billing guarantees. Confirm what the 4 TB allowance counts and alert well before the quota. Watch parties send small Socket.IO control state; every browser fetches authorized media from the selected source. No movie forwarding or movie transcoding is implemented on the VPS. Voice decoding/normalization is bounded audio processing only.

## Migration safety

There was **no migration history** in this repository. `00000000000000_baseline` records the original schema; `20261113000000_communications` expands it. They were generated by schema-file comparison, with no production connection. Communications SQL adds tables/columns/indexes and makes direct endpoints nullable for groups; historical values remain. Message text expands toTEXT. The three existing participant/receiver foreign keys explicitly preserve their original ON DELETE RESTRICT behavior even though their columns become nullable. This release does not introduce a new account-erasure policy. New reply/media references use SET NULL; new dependent tables use CASCADE. Review SQL and lock duration on a representative clone.

1. Obtain approved backup + restore rehearsal. Read-only introspection must compare the actual schema with the recorded baseline, including FK names, collations, defaults and indexes. Do not assume the repository equals production.
2. On an **empty disposable staging DB**, run `prisma migrate deploy` to apply both files. On an existing restored clone that matches the baseline, an authorized operator marks baseline applied with `prisma migrate resolve --applied 00000000000000_baseline`, then runs `prisma migrate deploy` for the expansion. Baseline resolution is a DB metadata write and requires release approval on production.
3. Exercise both old data and new groups/voice rows. Never `prisma db push`, `migrate reset`, or `migrate dev` on production.
4. Adopt the migration directory in the deployment pipeline. Do not automatically apply migrations from package postinstall/build. Production DDL is a separately reviewed release step.

## Staging services and configuration

Use `.env.example` as a secret-name inventory. Put actual secrets in a mode600 file/environment manager outside the repo. A Clerk development instance and signed webhook must create local user records. Netlify, socket and media API use the same environment-specific database and Clerk instance. Set exact APP_ORIGIN/SOCKET_ALLOWED_ORIGINS and MEDIA_ALLOWED_ORIGINS. Use separate service environments: local Next listens on 3000, socket on PORT=3001/SOCKET_HOST=127.0.0.1, and media on MEDIA_API_PORT=3002/MEDIA_API_HOST=127.0.0.1. Production Next stays on Netlify. Do not apply a socket PORT to another service. The socket must validate JWTs and refresh every 30 seconds; no legacy query-ID fallback exists. Deploy compatible client and socket versions for the earlier communications rollout; the media split itself preserves their protocol.

The standalone VPS media API serves `/api/chat/voice` and `/api/chat/media/*`; the frontend sends bearer-authenticated requests directly to its HTTPS origin. Netlify never processes or stores private audio. Existing public social Cloudinary uploads are preserved; private notes never use a public CDN. Install maintained FFmpeg+ffprobe only after infrastructure approval; use absolute binary paths and `/srv/goga/private-voice`, outside every webroot, owned by the unprivileged media service. Never expose it via an nginx static alias. Apply the reviewed 5 MiB proxy envelope limit while the API enforces 4 MiB audio plus bounded multipart overhead. Keep the media API loopback-only behind a dedicated CloudPanel HTTPS vhost, and preserve the existing socket listener/proxy. The [media runbook](VPS-MEDIA-DEPLOYMENT.md) provides exact staged commands and templates.

For coturn: stage a non-root/system service using distro-supported package, dedicated TLS certificate and a new TURN_SHARED_SECRET supplied securely. Enable short-lived HMAC credentials, no anonymous/open relay, no multicast/loopback/private peer destinations, a bounded UDP relay range, per-user/allocation quotas, bandwidth limits and logs without credentials. Review actual routing before opening 3478 UDP/TCP, 5349 TCP, and a narrow relay port range. Do not put TURN on 443 if CloudPanel already owns it. See `ops/coturn.conf.example`; it is a review template, not installed configuration. TURN browser credentials live 5 minutes and are refreshed by the client; rotate shared secret through an approved release.

For groups: provision self-hosted LiveKit on staging only, with private API keys, TLS/signaling and the documented WebRTC UDP/TCP reachability. `ENABLE_GROUP_CALLS=false` and `GROUP_CALL_SECURITY_REVIEWED=false` are defaults; the app refuses group media until both are explicitly reviewed. Cap 4 participants initially. Self-hosted LiveKit removing a participant does **not** inherently revoke issued/refreshed tokens. A 30-second issuance TTL does not bound all refreshed token reuse. Test and resolve this revocation limitation before enabling production; do not rely on expiry alone. [LiveKit token lifecycle](https://docs.livekit.io/frontends/reference/tokens-grants/).

WATCH_ALLOWED_HOSTS is an explicit approved source host list. Only HTTPS direct supported media URLs are accepted; the creator must confirm rights. Providers requiring DRM or subscription-player synchronization are not supported. This is separate from browser screen sharing, which obeys user permission and protected-content restrictions.

## Backups and restore rehearsal

Before production DDL, an authorized operator must capture an encrypted MySQL logical backup using the existing backup system or `mysqldump --single-transaction --routines --events --triggers --hex-blob` with credentials supplied by a private client option file, never command arguments. Confirm all relevant tables are transactional and stop schema changes for the backup window. Record MySQL version, schema/row counts, migration state, time and checksum. Copy the backup off the VPS; a same-disk copy does not protect against VPS loss.

Back up the persistent private voice directory and metadata consistently. Pause writes during the coordinated backup or use a tested snapshot strategy; missing media and orphan files must not be silently accepted. Preserve CloudPanel site/proxy configuration, process-manager definitions and secret-store recovery instructions separately, with restricted access. Do not commit any backup or secret to Git.

Restore into an isolated staging database/filesystem, run schema comparisons and representative social/chat/media reads, then apply the expansion and repeat. Record restore duration and a recovery point objective before approving release. Existing production data was not used in local validation.

## Release and rollback (only after explicit approval)

Build reproducible Linux artifacts in CI/staging for the VPS processes; deploy the frontend through the existing Netlify pipeline. Do not copy macOS native Prisma binaries to Ubuntu. Preserve CloudPanel's current process ownership, site config, database and environment. Record deployed commit, current release symlink, process manager, schema baseline, backup location and healthchecks before preparing the release. The voice API split has no DDL and requires no socket protocol switch. If the earlier communications migration still needs release, separately use a maintenance window that pauses app/socket writes during that DDL: three foreign keys are briefly dropped and recreated. Coordinate that earlier client/socket switch because the old unauthenticated socket protocol is intentionally rejected. Resume writes only after constraint and health checks pass.

For this voice split, an authorized operator installs the media service/proxy first and then the Netlify candidate configured with its HTTPS media origin. Verify app `/api/health`, existing socket `/health` and `/ready`, and media `/health` and `/ready`, then perform the two-user smoke test. Any still-pending additive schema migration and older socket protocol rollout remain separate approved operations. Watch error rates, DB connections, memory, disk, upload failures and call setup. No command in this repository deploys automatically.

For media-only rollback, follow the media runbook: keep app/socket infrastructure intact, select the previous compatible media release and Netlify deploy, and preserve files/metadata. The first standalone media release cannot roll back to ephemeral Netlify audio handling; disable voice temporarily if no compatible predecessor exists. For the broader communications rollback, disable group flags/new entry points and select compatible client/socket releases. **Do not reverse additive SQL or delete new messages.** An older client/server assuming non-null direct participants must be tested against expanded rows before rollback. Restore backups only through a reviewed incident plan, because restoration loses later writes. Keep media and DB metadata consistent and preserve the failed release for diagnosis.
